# ScreenShare — трансляция экрана по локал��ной сети

Приложение на C#, которое захватывает экран компьютера и передаёт его в реальном
времени по локальной сети через браузер. Пользователь открывает адрес, вводит
пароль и видит экран без установки дополнительного ПО.

Реализовано по техническому заданию «Разработка приложения для трансляции экрана
через Web-интерфейс в локальной сети».

---

## Транспорт: MJPEG (Вариант B)

Выбран вариант B — поток `multipart/x-mixed-replace` с JPEG-кадрами.

| | MJPEG (выбран) | WebSocket |
|---|---|---|
| Клиент | `<img src="/stream">`, JS не нужен | JS собирает Blob |
| Защита | работает с отключёнными скриптами | требует JavaScript |
| Задержка | чуть больше (целые кадры) | меньше |
| Сложность | минимальная | выше |

Ключевое свойство: **картинка идёт обычным `<img>`**, поэтому просмотр работает
даже если JavaScript заблокирован политикой браузера, и открывается с телефона
или планшета.

## Запуск

```powershell
cd ScreenShare
dotnet build ScreenShare.slnx -c Release
.\ScreenShare.Server\bin\Release\net10.0-windows\ScreenShare.exe
```

При старте программа печатает адрес, логин и пароль:

```
ScreenShare — трансляция экрана по локальной сети
==========================================================
 Мониторы:
   \\.\DISPLAY1       1920×1080  (основной)
 Захват:     10 fps, качество JPEG 70
 Клиентов:   максимум 8
 Пароль:     k3M9xPq2Rt
 Наблюдатель: vT7bHc2wQd   (только просмотр)
----------------------------------------------------------
 ВНИМАНИЕ: в трансляции видно всё содержимое экрана,
 включая открытые документы и введённые пароли.
 Не запускайте сервер в общих или гостиничных сетях.
```

Открыть в браузере: <http://192.168.150.147:8080>, пароль указан при запуске.

### Вход в браузере

Браузер спросит логин и пароль. **Логин можно вводить любой, даже пустой:**
роль определяет пароль, а не имя. Иначе пришлось бы каждому наблюдателю
вводить `admin` — имя чужое и одинаковое у всех.

Лучше вписать в логин своё имя: страница подхватит его автоматически как имя
для показа в панели «Кто смотрит», вводить его второй раз не придётся.

| Введено | Роль |
|---------|------|
| любой логин + пароль администратора | администратор |
| любой логин + пароль наблюдателя | наблюдатель |
| любой логин + неверный пароль | 401 |

### Две роли: администратор и наблюдатель

Программа различает **два уровня доступа** — это позволяет дать коллегам
смотреть трансляцию, не выдавая им управления чужим экраном:

| | Администратор | Наблюдатель |
|---|---|---|
| Смотреть трансляцию | ✅ | ✅ |
| Статистика, список клиентов | ✅ | ✅ |
| **Запустить / остановить** | ✅ | ❌ 403 |
| **Изменить FPS, качество, монитор, курсор** | ✅ | ❌ 403 |
| Кнопки управления в панели | видны | скрыты |

Оба пароля печатаются при запуске. Наблюдателю сообщается только его пароль —
администраторский остаётся у вас. Логин при этом вводится любой: он не
влияет на права и лишь подсказывает странице имя для показа.

Права проверяет сервер, а не страница: кнопки у наблюдателя просто не
отрисовываются, но даже если отправить запрос вручную, сервер вернёт 403.

Сделать всех администраторами (например, для домашнего просмотра):

```powershell
ScreenShare.exe --no-viewer-role
```

### Как наблюдатель называет себя

В шапке страницы есть поле **«Как вас зовут?»**. Имя уходит на сервер и
показывается администратору в панели **«Кто смотрит»** — вместе с адресом,
объёмом принятого и временем подключения:

```
КТО СМОТРИТ
Анна Иванова                              192.168.150.31   3.0 МБ   12 мин
Борис                                     192.168.150.44   1.5 МБ   3 мин
Наблюдатель 3                             192.168.150.77   512.0 КБ только что
```

Если имя не задано, показывается автоимя — по порядковому номеру подключения.

Имя берётся из логина окна входа, но **только если логин изменился** с
прошлого захода. Так сохраняются оба ожидания: человек, вписавший своё имя в
логин, видит его сразу, а вписанное им же имя в самом поле не затирается
при каждой загрузке страницы.

Имя приходит в cookie: поток открывается обычным `<img>`, заголовки к нему из
браузера добавить нельзя, а cookie уходит вместе с запросом картинки. Поэтому
после смены имени поток переоткрывается — иначе в списке осталось бы прежнее.
Имя сохраняется и в самом браузере, так что повторно вводить его не нужно.

Имя — чужие данные, поэтому проверяется на сервере: обрезается до 32 символов,
вырезаются управляющие символы, разметка и кавычки, в списке выводится через
`textContent`. Проверку на браузере подделать нельзя: если бы она была там,
её можно было бы обойти, отключив скрипты.

### Параметры командной строки

| Параметр | Описание | По умолчанию |
|----------|----------|--------------|
| `-p, --port <порт>` | порт HTTP-сервера | 8080 |
| `--password <пароль>` | пароль администратора | случайный, 10 символов |
| `--viewer-password <пароль>` | пароль наблюдателя (только просмотр) | случайный, 10 символов |
| `--no-viewer-role` | один пароль на всех, без разделения ролей | разделение ролей включено |
| `--user <имя>` | логин по умолчанию, если поле оставлено пустым | admin |
| `--fps <1…60>` | кадров в секунду | 10 |
| `--quality <10…100>` | качество JPEG | 70 |
| `--max-width <px>` | ограничить ширину кадра | без ограничения |
| `--max-height <px>` | ограничить высоту кадра | без ограничения |
| `--max-clients <1…100>` | максимум клиентов | 8 |
| `--monitor <имя>` | монитор для захвата | основной |
| `--no-cursor` | не рисовать курсор | курсор виден |
| `--local-only` | слушать только 127.0.0.1 | доступен по сети |
| `--fixed-password` | не генерировать пароль; **требует** `--password` | пароль генерируется |
| `-h, --help` | справка | — |

Ключ `--fixed-password` без `--password` больше не запускает программу: пароль
получился бы пустым, и трансляцию открыл бы кто угодно без запроса на вход.
Теперь выводится понятная ошибка и код возврата 1.

Пример для слабого канала:

```powershell
ScreenShare.exe --fps 5 --quality 45 --max-width 1280 --max-clients 3
```

### Почему нет WebRTC

Пункт 3.2 предлагает WebRTC через SIPSorcery, но медиатрек видео в этой
библиотеке требует нативного кодировщика **libh264**, которого нет в
поставляемой сборке и который нельзя распространять вместе с лабораторной
работой. Без него SIPSorcery умеет только принимать видео, но не кодировать
кадры в H.264 для отправки.

Вариант «отдать JPEG через WebRTC DataChannel» технически возможен, но это не
то, что подразумевается под WebRTC в задании: не будет ни видеотрека, ни
трансформации, ни стандартного `getUserMedia`-приёмника.

Поэтому основной транспорт — MJPEG, а WebRTC оставлен нереализованным, вместо
того чтобы делать вид, что функция работает. Требования базового уровня от
этого не страдают: п. 3.1 полностью выполнен.

## HTTP API

| Метод | Путь | Назначение |
|-------|------|------------|
| `GET` | `/` | страница просмотра |
| `GET` | `/stream` | MJPEG-поток кадров |
| `GET` | `/api/status` | состояние, статистика, список мониторов |
| `GET` | `/api/frame.jpg` | один кадр отдельным JPEG |
| `GET` | `/api/interfaces` | мониторы и сетевые адреса |
| `GET` | `/api/me` | логин, роль и сохранённое имя |
| `POST` | `/api/viewer/name` | сохранить имя наблюдателя (в cookie) |
| `POST` 🔒 | `/api/start` | запустить захват |
| `POST` 🔒 | `/api/stop` | остановить захват |
| `POST` 🔒 | `/api/settings` | изменить FPS, качество, размер, монитор, курсор |

Все маршруты, кроме корня, требуют пароля. 🔒 — только для роли
администратора: наблюдатель получает **403 Forbidden**.

Поле `clients` в `/api/status` администратору отдаётся целиком, наблюдателю —
пустым: там имена и адреса других людей, а роль наблюдателя на них не даёт
смотреть.

Пример:

```bash
curl -u admin:пароль -X POST http://localhost:8080/api/settings \
     -H "Content-Type: application/json" \
     -d '{"fps":15,"quality":60,"maxWidth":1280}'
```

│
└─ ScreenShare.Server\                  веб-сервер (ScreenShare.exe)

   ├─ MjpegStream.cs                     поток multipart/x-mixed-replace

### Как кадр доходит до клиента

```
цикл захвата (поток)
   │  CopyFromScreen → JPEG
   ▼
FrameHub ──► канал клиента 1  (глубина 1, DropOldest)
          ──► канал клиента 2
          ──► …
   ▼
MjpegStream: --boundary… Content-Length… <байты JPEG>
   ▼
браузер: <img src="/stream">
```

**Очередь глубиной 1 с вытеснением** — ключевое решение. Если клиент не
успевает забирать кадры (медленная сеть, телефон), следующий кадр вытесняет
предыдущий. Если бы кадры копились, картинка отставала бы на секунды, а при
восстановлении связи «догоняла» бы разом. Для трансляции живого видео
пропуск устаревшего кадра всегда лучше задержки.

### Ресурсы GDI+

Растр переиспользуется между кадрами, пока не изменится разрешение. Создание
нового `Bitmap` на каждом кадре приводит к росту потребления GDI-ресурсов и
утечкам в длительной трансляции.

Владелец растра — **только поток захвата**. `InvalidateSurface()` лишь
ставит флаг, а пересоздание выполняет цикл захвата: иначе смена настроек из
потока HTTP освободила бы растр в момент, когда в него рисует захват.

### Качество и трафик

Измеренные значения для 1920×1080:

| Качество | Размер кадра | Трафик на 1 клиента при 10 fps |
|----------|--------------|---------------------------------|
| 85 | ~180 КБ | ~1,8 МБ/с |
| 70 | ~115 КБ | ~1,15 МБ/с |
| 50 | ~75 КБ | ~0,75 МБ/с |
| 30 | ~45 КБ | ~0,45 МБ/с |

Для экономии трафика снижайте `--max-width`: картинка 960×540 читается почти так
же, но весит заметно меньше. Проверено: разрешение меняется на лету, без
перезапуска трансляции.

### Показатели на лету: `recentFps` и `recentFrameBytes`

В `/api/status` две пары значений, и они отвечают на разные вопросы:

| Поле | Что показывает |
|------|----------------|
| `averageFps`, `averageFrameBytes` | сколько ушло **за всё время работы** |
| `recentFps`, `recentFrameBytes` | сколько уходит **сейчас** |

Это не одно и то же, и разница была замаскированной ошибкой. Кумулятивное
среднее не сбрасывается при смене настроек: если уменьшить качество с 70 до
15, оно медленно поползёт вниз, усредняя новые кадры со старыми. Панель при
этом показывала бы почти прежнее значение — выходит, что «качество не
меняется», хотя оно менялось исправно. Панель показывает `recent*`.

Для самой смены частоты важно другое. Интервал между кадрами берётся из
настроек, и раньше он считывался **один раз перед циклом захвата**. В цикле
использовалась запомненная переменная, поэтому новый FPS просто не мог
сработать: в настройках появлялось «30», а кадры продолжали идти с прежней
частотой. Теперь интервал читается на каждой итерации. Качество от этого не
страдало: `CaptureOnce` читает настройки каждый раз заново.

## Два компьютера ведут трансляцию одновременно

Ничего не конфликтует: порт занимается на каждом компьютере отдельно, а адрес
в ссылке строится из IP самого компьютера. Получатся две разные ссылки, и
каждая ведёт к своему экрану.

Конфликт возможен только если запустить **два экземпляра на одном компьютере**
с одинаковым портом. Раньше программа в этом случае падала стеком трассировки
после того, как уже напечатала адрес и пароли, — то есть сообщала об успехе и
умирала. Теперь адрес печатается **после** успешного запуска сервера, а при
занятом порте выводится:

```
  Порт 8080 уже занят другим процессом.

  Закройте прежний экземпляр или выберите другой порт:
      ScreenShare.exe --port 8081

  Кто слушает этот порт:
      netstat -ano | findstr :8080
```

Код возврата — 1, баннер не печатается, уже работающий экземпляр не трогается.

## Если не открывается с другого устройства

Самая частая причина: **брандмауэр Windows блокирует входящие соединения.**
По умолчанию они запрещены, и программа без явного разрешения туда не попадает.
При этом `localhost` на самом компьютере работает всегда — поэтому проблема
выглядит загадочно и часто ищется не там.

Проверьте порядок действий:

1. Сервер запущен, в консоли напечатан адрес вида `http://192.168.150.147:8080`.
   Если вместо этого `127.0.0.1`, перезапустите без ключа `--local-only`.
2. Адрес открывается **на самом компьютере** через `http://localhost:8080`.
   Если и это не работает — смотрите пароль.
3. С другого устройства в той же сети не открывается — нужен пункт 4.
4. Добавьте разрешение в брандмауэр **от имени администратора**:

```powershell
netsh advfirewall firewall add rule name="ScreenShare (входящие)" dir=in action=allow protocol=TCP localport=8080 program="C:\путь\к\ScreenShare.exe"
```

Программа проверяет наличие такого правила при запуске и, если его нет,
печатает эту же команду подсказкой.

Убрать правило, если оно больше не нужно:

```powershell
netsh advfirewall firewall delete rule name="ScreenShare (входящие)"
```

Если устройства в разных подсетях или включена изоляция клиентов на
коммутаторе (AP isolation, guest-сеть), трафик не дойдёт даже с разрешением —
это уже настройка сети, а не программы.

## Безопасность

Трансляция экрана показывает **всё**: открытые документы, почту, введённые
пароли. Поэтому:

- пароль генерируется случайно при каждом запуске, если не задан явно;
- пароли администратора и наблюдателя **разные**: общий пароль лишил бы
  разделение ролей смысла — наблюдатель снова смог бы остановить трансляцию;
- сравнение пароля — постоянного времени (`CryptographicOperations.FixedTimeEquals`),
  иначе по времени ответа можно подбирать пароль посимвольно;
- статистика и адреса клиентов тоже защищены паролем;
- наблюдатель не может остановить трансляцию или изменить параметры:
  ограничение проверяется политикой авторизации на сервере;
- имена и адреса других наблюдателей доступны только администратору;
- имя наблюдателя очищается на сервере: длина, управляющие символы,
  разметка и кавычки; вывод через `textContent`;
- рекомендуется `--local-only`, если трансляция не нужна другим устройствам.

Что **не** защищено: сам HTTP без HTTPS. Пароль передаётся в заголовке
`Authorization` в открытом виде. Для лабораторной работы в доверенной сети это
приемлемо, но в публичной сети использовать нельзя.

## Проверено в работе

- захват 1920×1080, 10.2 fps, 0 ошибок
- MJPEG-поток: 101 целый JPEG-кадр за 10 секунд, 1,15 МБ/с
- Basic Auth: без пароля и с неверным — 401, с верным — 200
- смена FPS, качества и разрешения на лету, без остановки
- лимит клиентов: третий клиент получает 503
- курсор, статистика и панель настроек в браузере
- остановка и повторный запуск: захват останавливается и снова начинается,
  счётчики кадров не обнуляются, средний FPS не завышается
- изменение настроек на лету, измеренное по кадрам, а не по отчёту:

  | Задано | Частота (факт.) | Кадр (факт.) |
  |--------|-----------------|--------------|
  | 10 fps, качество 70 | 10,17 | 122,4 КБ |
  | 25 fps, качество 100 | 22,33 | 407,5 КБ |
  | 4 fps, качество 10 | 4,17 | 54,1 КБ |
  | 12 fps, качество 60 | 12,17 | 108 КБ |

- раздельные права: наблюдатель читает страницу, поток, статистику и кадры
  (200), но получает 403 на `/api/start`, `/api/stop` и `/api/settings`
  — в том числе при корректно сформированном теле запроса
- в браузере у наблюдателя не отрисовываются кнопки «Запустить»,
  «Остановить» и панель настроек; ошибок в консоли нет
- трансляция наблюдателя идёт с той же частотой: 50 целых JPEG-кадров за 5 с
- список клиентов: администратель видит имена, наблюдатель получает пустой
  массив при том же ненулевом счётчике
- имя наблюдателя доходит до администратора и переживает смену: кириллица
  сохраняется байт в байт (проверено по hex), смена имени обновляет список
- очистка имени: `Анна Иванова` → `АннаИванова`, `a/b\c[d]{e}` → `abcde`,
  `Маша "Милая"` → `Маша Милая`, 100 символов → 32, пустое → автоимя
- `--fixed-password` без `--password` — понятная ошибка и код возврата 1
- два экземпляра на одном порту — понятная ошибка, код возврата 1, баннер
  не печатается, первый экземпляр продолжает работать
- вход в браузере: логин `admin`, `Анна`, `root` и пустой пропускают и с
  паролем администратора, и с паролем наблюдателя; роль определяет только
  пароль, неверный пароль даёт 401 при любом логине
- имя из поля входа подхватывается страницей и доходит до панели
  администратора без дополнительного ввода

## Отклонение от ТЗ

В задании указан .NET 8; в системе установлен только .NET 10 SDK, поэтому
проект нацелен на `net10.0-windows`. Код не использует возможностей,
появившихся после .NET 8, и переносится сменой строки `TargetFramework`.

Разделение ролей администратор / наблюдатель в ТЗ не запрашивалось и
добавлено сверх задания: пароль в исходном варианте давал одинаковые права
всем вошедшим, то есть любой зритель мог остановить трансляцию. Ключ
`--no-viewer-role` возвращает прежнее поведение.

Имя наблюдателя и панель «Кто смотрит» тоже добавлены сверх ТЗ. Список
подключившихся API отдавал и раньше, но на странице не показывался.
